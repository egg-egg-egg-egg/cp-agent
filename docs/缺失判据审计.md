# 审计：把「缺失」当成「不存在」

> 2026-09-29 立项。起因是 `--prune-diff` 删掉 `#057` 时连带销毁了 PID `19716`（详见下）。
> 这份清单是该病的**全项目普查**结果 + 逐条解决方案。
> **修完一条就划掉一条，全清后本文件即可删除**（它不是长期参考，是待办）。

## 统一病因

这五处犯的是同一个错：**用「存在性」这个只有 1 bit 表达力的判据，去承载需要更多状态的东西。**

| 真实需要的语义 | 被压缩成 | 丢失的是什么 |
|---|---|---|
| 已检查 / 未检查 / 无法检查 | 文件在不在 | 把「没检查」渲染成「检查通过」 |
| 最新 / 过期 | 副本在不在 | 把「副本过期」渲染成「已完成」 |
| 冲突 / 一致 | 有没有这一行 | 把「两个源不一致」渲染成「事实不存在」 |

**通则**：凡是「缺失」可以由**多种原因**造成的判据，一律升级为**三态**
（通过 / 失败 / **无法判定**），且 **「无法判定」默认不等于「通过」**。

## 1. `pipeline.py:1194` — 缺 `problem.yaml` ⇒ 跳过两个质量门禁，汇总仍报 `✅ ALL PASSED` 【最危险】

**现状**

```python
# 质量检查步骤：需要 problem.yaml（write_metadata 产物），存量题目缺失时跳过并警告
if (self.d / "problem.yaml").exists():
    steps.append(("data_strength", self._step_data_strength))
    steps.append(("final_check", self._step_final_check))
else:
    print("  ⚠ 无 problem.yaml，跳过 data_strength/final_check（可先用 write_metadata 生成）")
```

而汇总处：

```python
summary = {..., "all_passed": all(results.values())}
status = "✅ ALL PASSED" if summary["all_passed"] else "❌ FAILED"
```

被跳过的步骤**压根不进 `results`**，所以它们不参与判定 —— 一个刚手写、还没跑 `write_metadata`
的目录，跑完流水线会打印 **`✅ ALL PASSED`**，而「数据强度」和「最终检查」**从来没跑过**。

**危害**：最高。这是我们记忆里那条「先写 yaml 再跑第二轮」的由来 —— **靠人记住的规则，
就是迟早会忘的规则**。

**方案**

- 让「跳过」成为**显式的第三种状态**：`results[name] = None`，汇总区分 `passed / failed / skipped`；
- `all_passed` 只在**没有 skipped** 时为真；或改名 `no_failure` 并另加 `complete` 布尔，二者都要看；
- 更彻底：`problem.yaml` 缺失时**直接 fail** —— `write_metadata` 是流水线的必需步骤之一，
  「跳过」这个分支本就不该存在。若确要保留，加显式开关 `--allow-missing-metadata`，默认不许。

## 2. `problem_gate.py:116` — 缺 `result.json` 只告警并按「降级」放行 ⇒ 门禁有后门

**现状**

```python
if not os.path.exists(rj_path):
    warn.append("缺 result.json（非 CI 产物？）—— 质量判据降级为只看 problem.yaml")
    rj = None
```

这是 `warn` 不是 `fail`，默认放行（只有 `--strict` 才拦）。

**危害**：**只要不放 `result.json`，所有由 CI 结果驱动的硬检查全部失效**
（validator 未过 / 样例未全过 / data_strength 未过 / in-out 不配对）。门禁从「证据驱动」
退化成「文件存在性驱动」—— 而它守的正是「脏数据不能进看板」这条线。

**注意**：门禁对 `problem.yaml` 和其他必需文件的缺失**处理是正确的**
（`problem_gate.py:110-112` 直接 `fail`）。所以这不是疏忽，是**这一条**被当成了例外。

**方案**

- **证据缺失必须是不通过，不是告警。** 分两种情形处理：
  - 产物来自 CI（能从 artifact 名 / run_id 认出）却缺 `result.json` ⇒ **硬失败**（产物被截断或篡改）；
  - 确实存在「非 CI 产物」（手写题）⇒ 要求**显式声明来源**（如在 `problem.yaml` 里写
    `source: manual`），声明后才允许降级。**不允许「因为文件不在就默认降级」。**

## 3. `build_records.py` 的 `--prune-diff` — 已实证销毁了 PID 19716 【已发生】

**现状**

```python
if str(r["pid"]).strip() in ("", NO_PID):
    continue                      # 库里从未记过 PID → 视为未产出，保留
```

判据 = 「目录不存在 **且** `uploaded_pids.txt` 无该行 **且** 库里 `平台PID≠无PID`」。
⇒ **恰好在两个源不一致时才触发删除。**

**已实证的损失（2026-09-29 查证）**

```
uploaded_pids.txt:  dp_1500_1=19715
                    dp_1500_86=19717      ← 19716 缺号
                    dp_1500_91=19718
```

- 记忆记录 `#057 dp_1500_80` 的 PID 就是 **19716**，正好夹在两道**我们自己的连续上传**之间；
- 查 OJ（`oj_check.py`）：`19714 / 19715 / 19717 / 19718` **都在**，**19716 已不存在**
  ⇒ 该题上传过、**后来被删掉了**，不是孤儿活题。
- 对照组：`19779 / 19780 / 19790 / 19800` 在 OJ 上存在但**不在我们的表里**
  ⇒ **pid 空间与其他用户共享，缺号大多是别人的题**，不能一概当成"我们丢过记录"。
- ⇒ `#057` 是**唯一**一个能确证被销毁的记录，而**现在能说出"19716 曾是 dp_1500_80"，
  靠的是人的记忆文件，不是任何机器产物**。机器产物删了就是删了。

**附加发现**：`--prune-diff` 的实现住在 `.workbuddy/skills/problem-dashboard/scripts/build_records.py`
—— 而 `.workbuddy/` **被 gitignore** ⇒ **这段"删能力"既没有版本历史、也没有 code review**，
CI 也看不见它。一个能删线上数据的判据，不该住在版本控制之外。

**方案**

- 判据改为 **「冲突即告警、不自动删」**：文件无行 + 库有 PID ⇒ 输出**待核查清单**
  （新增 `--prune-report`，只打印不产 payload）；只有两个源**都**说"没有"时才产出 delete payload，
  并给它加 `--yes` 二次确认。
- 把 `--prune-diff` 的实现**移出 `.workbuddy/`**（学 `problem_gate.py` 的做法：移到仓库根
  `dashboard_prune.py` + `py-modules` 登记），让它进 git、进 CI。

## 4. `dedup.py:40` / `dedup.py:340` + `agent.py:269` — 查重不可用 ⇒ 静默降级，完成门禁只看「调用过」

**现状（三处联动）**

```python
# dedup.py:43 —— tasks.yaml 读取失败
except Exception as e:  # noqa: BLE001 — 任何异常都降级，不中断出题
    return {"success": False, "disabled": True, "query": query,
            "message": f"轻量召回不可用（tasks.yaml 读取失败：{e}）；本次跳过查重。"}

# dedup.py:340 —— 自建题入库
"""把生成成功的题目写入本地题库索引……题库数据不存在时静默跳过。"""

# agent.py:269 —— 完成门禁
elif not quality_state["search_attempted"]:
    print("  ✗ 完成门禁：从未调用 search_problem_db 查重")
```

门禁判的是 `search_attempted`（**是否调用过**），**不是**「是否真的查到了」。
`disabled: True` 的返回也会把 `search_attempted` 置真 ⇒ **查重整体不可用时，完成门禁照样放行**。

**危害**：CI 上 `problem_data/` 不在 ⇒ 题库为空 ⇒ **批量出题自撞**，
而门禁给的是绿灯 —— 我们记忆里记的是「查重是静默降级」，实际比这更糟：**它是"降级 + 放行"**。

**方案**

- 把 `disabled` 与「查过了、没撞」**彻底分开**：门禁改为要求
  `search_attempted and not dedup_disabled`；
- `disabled` 时在 `result.json` 落显式标记（如 `"dedup": "unavailable"`），
  让门禁 / 看板都能据此判定「这题的查重其实没做」；
- CI 上若要批量出题，**宁可先失败**（提示去挂 R2 / Hugging Face 题库），
  也不要静默放行自撞 —— 撞出来的题是返工成本最高的那类脏数据。

## 5. （邻居类）`pipeline._compile()` — 用「副本不存在」判断「需要拷贝」

**现状**

```python
if os.name == "nt" and not out.exists():     # out = bin/<name>，无扩展名
    exe = out.with_name(out.name + ".exe")
    if exe.exists():
        shutil.copyfile(exe, out)
```

真实语义应是**「副本是否比源新」**，实际判的是**「副本是否存在」**。
⇒ 第一次编译后 `bin/generator` 已存在，此后 g++ 只更新 `generator.exe`，
`bin/generator` **永远是旧二进制**。症状：改了源码重跑，数据毫无变化、
`data_strength` 一直报「数据太弱」，极难定位（这是我们记忆里的头号坑）。

**方案**：改成 mtime 比较（`out.stat().st_mtime < exe.stat().st_mtime` 才拷贝），
或者干脆去掉这层兜底 —— 每次编译后都重新拷贝一次，代价是一个文件复制。

## 对照：做对了的地方（可作模板）

- `problem_gate.py:110-112` —— 缺必需文件 / 缺 `problem.yaml` ⇒ **硬失败**。
- `dedup.py:350` —— `problem.md` 不存在 ⇒ `{"success": False, "message": "problem.md 不存在"}`，**明确报失败**。
- `report.py` —— 无「缺失即跳过」模式。

**同一个「文件不存在」，门禁选择报错、流水线选择跳过。** 这就是全部问题的缩影：
不是不知道该怎么办，而是**同一个事实在不同模块被判成了不同的东西**。

## 建议实施顺序

1. **第 3 条（prune）** —— 唯一已经造成不可逆损失的，且改动最小（改成只报不删）。
2. **第 1 条（流水线三态）** —— 最危险的假绿灯，且它保护的是「数据强度」这道核心质量线。
3. **第 2 条（门禁后门）** —— 有现成测试基建（`tests/test_problem_gate.py`），改动可验证。
4. **第 4 条（查重降级 + 门禁）** —— 跨 `dedup.py` / `agent.py` 两处，需要一起改才成立。
5. **第 5 条（`_compile` mtime）** —— 独立小修，随时可做。

**每条都要带测试再落地**（学 `tests/test_problem_gate.py` 的方式：直接断言 + round-trip，
不要写「两条路对拍一致」那种测不出假阴性的测试）。
